# 建站需求发现：ABCD

作者：Kevin Shu · GitHub：kevinshu09

这是自足的建站版 Buddha 流程，不需要额外安装其他技能。目的在于帮助用户发现真实需求和可行答案，不是机械延长访谈。

## 适用范围与用户控制

完整新建网站默认执行 A→B→C→D，再进入建站实施。已有项目发生定位、主要功能、数据用途或维护责任等重要变化时，只重访受影响部分。改标题、替换图片、增加已明确的下拉选项等小修改直接执行与验证，不重新要求三轮问答。

用户明确要求缩短、跳过或停止提问时立即尊重；将未确认项标为 `[未知]` 或 `[假设：待确认]`，用现有事实形成阶段产物。不把时间流逝当作同意。若未知项影响购买、公开发布、真实数据处理或其他需明确授权的操作，只暂停该操作，继续不依赖它的工作。

不重复询问对话中已有答案。不可把个人偏好、预算或目标编成用户事实。每轮说明当前阶段；每个阶段展示简明产物并让用户确认或修正后进入下一阶段。已有明确授权不重复确认；用户授权压缩流程时可合并呈现，不强迫逐步回复。

## Phase A：三轮需求发现

正常进行三个相互衔接的问答回合，不将三轮一次性堆给用户。每轮优先问会改变方案的问题，已有答案直接引用。可参考第一轮 6–8 题、后两轮各 5–7 题，但不为凑数量重复提问。

1. **事实层**：服务谁、提供什么、访客要完成什么行动、现有渠道与素材、语言、期限、预算、成功标准。
2. **动机与约束层**：针对上一轮追问为何选择这个目标；不能公开什么；由谁维护；已有账号和系统；哪些功能必需；谁决策。
3. **压力测试层**：针对用户关键判断提出反例。没有自然流量怎么办？用户不愿填表怎么办？没有时间维护怎么办？预算减少先去掉什么？哪个假设最缺证据？

提问用于辨别需求，不预设一定需要网站、复杂功能、付费平台或特定视觉风格。

产出 `Phase A 事实表`：目标、受众、主要行动、已核实内容、资源、约束、维护责任、用户偏好、成功标准，以及独立的未知/待验证清单。用户提前停止时注明实际完成轮数，不虚称完成三轮。

通过条件：事实与假设分开；关键缺口明确；用户有机会修正；继续范围与授权一致。

## Phase B：展开方案与后果

引用已确认的 A 事实表。先列至少三条有实质差异且与需求相关的路径，加一条“不建／维持现状”。例如展示站、询盘站、预约站；这只是示例，不能强行让不相关方案入选。每条写出主要步骤、资源、失败模式、可逆性与未知依赖。

列出候选决策节点，依据失败代价、不确定性和未经验证的默认判断，选择最高的 1–2 个展开：
- **L0**：根决策，例如是否现在收集客户资料。
- **L1**：不同主路径，包含一个非默认选项。
- **L2**：每条相关路径内的具体选择。
- **L3**：选择产生的直接后果，以及由后果触发的新决策。
- **L4**：失败链、责任、成本与依赖。
- **L5**：对整体目标、上线时间、维护和信任的连锁影响。

不能只列六个标签；后果必须连接到下一个决策。低风险节点列到 L2 即可。平台规则、价格和技术能力须核实或标 `[需验证]`。

每层立即记录可见的“苦→集→灭”：具体阻碍、根因选择、可替代分支。不要等选好方案后再补理由。查找并写出一个新发现的选项；如果没有，重查假设和遗漏，仍无新选项则如实说明，不凭空制造创新。

当新答案改变关键条件时，回到受影响节点重钻，标明哪些分支被剪掉、复活或新增。A 尚未结束时先更新事实和受影响节点记录，不提前给出最终方案。

自行决定的关键文案、结构、视觉或表单方案，先给至少三个方向不同的候选，注明弱点和选择依据；用户已指定的内容保持不变，必要时仅比较措辞。不为每行代码或小改动制造三套实现。

产出：`Phase B 候选节点清单`、`Phase B 五层下钻：节点名`、`Phase B 新选项`、跨路径依赖、扩散→筛选记录。

进入 C 前检查：主要路径已比较；关键节点有真实后果链；新选项或未发现原因已说明；假设已标记；尚未把未选方案当成最终网站实施。

## Phase C：筛选出可执行方案

引用 B 的路径和节点，逐条列出：
- **苦**：哪一个具体后果阻碍用户目标。
- **集**：哪个上游选择或假设造成它。
- **灭**：放弃整条路径，还是修改中间步骤能够解决。
- **道**：保留下来的可执行路径。

依据 A 的目标与资源筛选，不把个人审美当作用户需求。留下无法消除的风险、预案和止损检查点。例如无法确认服务条款允许收集某类资料时，先不启用该字段。

在对话里完整显示推荐的执行步骤，不只提供文件链接。让用户修正方案；关键决定能追溯到 A/B。若关键未知会改变结论，先验证，不能硬选。

产出 `Phase C 剪枝记录` 与确认后的建站计划：页面和主要内容、功能与数据流、视觉方向、技术与托管、维护边界、验收条件、发布范围。

## Phase D：私人记录与持续回填

先确认记录目录是否会被 Git 跟踪、自动部署、云盘同步或共享；“本地”不等于“私有”。优先在公开仓库与部署根目录之外写 `runs/YYYYMMDD-项目短名.md`，保存 A 事实表、未知项、B 方案与后果链、C 选择及原因、执行计划。记录实际完成范围，不虚构用户确认。

留出 `后续实际结果`，在实施、验证和上线后更新。只做普通文件记录，不建立向量库或 RAG，不收集不必要的个人信息，不写密钥值。

用户明确不希望保存时，不落盘；在对话中给出必要摘要，并记录用户选择不保存，不将落盘作为继续工作的前提。忽略规则不能移除已经跟踪的文件；不要擅自删除用户既有记录。已有聊天和服务日志不因不落盘而消失。

D 是决策存档，不是网站已经完成。C 确认、D 初始记录后进入主技能的内容、设计、实现、表单、验证、发布和交接。实际执行遇到新事实时，返回受影响阶段并更新记录。

决策记录、原始聊天、预算、私人资料和部署配置不进入公共网站或通用技能包。用户要求公开其中内容时，先制作并核验单独的脱敏版本。
